# HeavyChat Demo Login Routing Study

- **Created:** 2026-09-29T12:45:19+00:00
- **Status:** Study complete; the user requested a fix for the login 404.
- **Scope:** Route Django's authentication login URL, provide a usable login form, define safe post-login/logout destinations, and add regression tests/documentation.

## Verified Facts

- `@login_required` protects the chat home and other application views. Django defaults unauthenticated redirects to `/accounts/login/?next=...`.
- `heavychat.urls` currently routes only admin and chat URLs; `/accounts/login/` is missing, which directly explains the reported 404.
- Django auth, sessions, middleware, and app-template discovery are enabled. The project has no registration/login template.
- `LOGIN_REDIRECT_URL` is not configured, so visiting the login page without `next` would otherwise fall back to `/accounts/profile/`, which is also not routed.
- The worktree is on `main` and clean except for a pre-existing untracked `session-ses_f13a.md`; preserve it and do not include it in this fix.

## Tradeoffs and Risks

- Include Django's built-in auth URLconf instead of implementing password verification/session handling in a custom view. Provide a project-owned login template with CSRF protection and a hidden `next` field.
- Set explicit successful-login and logout destinations so both direct login visits and protected-page redirects land on valid routes.
- Login remains limited to existing seeded users; no public registration or password-reset flow is added. A live provider key is still required for completions, but not for signing in or using local UI features.
- The demo password is generated and printed only on first user creation. If it was not saved, it must be reset locally; this fix should not reveal or rotate credentials automatically.

## Assumptions and Open Questions

- The reported `/accounts/login/` path is generated by `login_required`, not by a proxy or custom middleware.
- The appropriate successful-login destination is the HeavyChat home route `/`; the login view should still honor Django's validated `next` parameter.

## Decision

Use `django.contrib.auth.urls`, configure valid login/logout redirect paths, add a styled CSRF-protected `registration/login.html`, and test both unauthenticated redirect and successful login/session access. Update operations documentation with the login route and credential-reset guidance. Keep the pre-existing session export file untouched.
